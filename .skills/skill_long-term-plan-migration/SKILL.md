# 长期计划迁移

## 任务目标

- 本 Skill 用于：将用户已选定的长期计划迁移到当前环境并重新规划日程
- 能力包含：准备目标路径、执行文件复制、解读计划文件、重新规划日程
- 前置条件：Agent 已通过 `long_term_plan_list` 工具查询到计划列表，且用户已确认要迁移的计划
- 触发条件：用户已选定需要迁移的计划，进入迁移执行与日程重建阶段

## 操作步骤

严格按以下两个阶段顺序执行，每个阶段完成后方可进入下一阶段。

### 阶段一：准备路径与执行文件复制

#### 1.1 生成默认目标路径

对用户选中的每个计划，按以下规则生成默认目标路径：

- **目标路径**：`长期计划/{plan_name}/`
- **重名处理**（强制）：若本次选中的计划中存在名称相同但 id 不同的情况，为重名计划的 `{plan_name}` 追加创建时间后缀，格式为 `{plan_name}_{创建时间}`（如 `英语学习_20250101`）；名称唯一的计划无需后缀
- 禁止将两个 id 不同但同名的计划迁移到同一文件夹下

#### 1.2 确认路径

告知用户将把历史长期计划的文件迁移到对应文件夹，例如：

```
计划"英语学习"的文件将迁移到 长期计划/英语学习/
计划"读书计划"(2025-01-15创建)的文件将迁移到 长期计划/读书计划_20250115/
计划"读书计划"(2025-03-01创建)的文件将迁移到 长期计划/读书计划_20250301/
```

询问用户是否需要调整，等待确认后继续。

#### 1.3 执行迁移

1. 对每个计划调用 `long_term_plan_migrate` 工具，传入确认后的目标路径
2. 对每次调用：
   - 记录工具返回的目标路径（后续阶段依赖此路径，以下称 `{目标路径}`）
   - 确认复制是否成功
   - 若失败，向用户报告错误并询问是否继续迁移其余计划
3. **更新 spec.txt 中的路径**：对每个成功迁移的计划：
   - 在 `{目标路径}/history/spec.txt` 末尾追加一行，记录迁移后的目标路径：`迁移目标路径：{目标路径}/`
   - 检查 spec.txt 内容中所有文件路径表述，将旧路径全部替换为 `{目标路径}/{原文件或文件夹名称}`
4. 全部完成后汇报迁移结果（成功/失败的计划及路径）

### 阶段二：分派后台任务进行计划分析与日程规划

为每个成功迁移的计划创建一个独立的后台任务，多个计划并行推进。

#### 2.1 分派后台任务

对每个成功迁移的计划，创建一个后台任务，传入以下任务指令：

> 你需要分析长期计划「{plan_name}」的历史文件并生成日程规划建议。按以下步骤执行：
>
> **步骤一：阅读 spec.txt**
> 读取 `{目标路径}/history/spec.txt`，提取计划的最终目标、范围约束、里程碑、时间要求和依赖条件。
>
> **步骤二：阅读历史文件**
> - 读取 `{目标路径}/history/calendar_events.jsonl`，提取已安排/已完成的事项、时间分布、执行节奏、**历史日程的任务描述**（作为后续创建新日程时的描述参考）
> - 读取 `{目标路径}/history/log.jsonl`，提取已完成任务、当前进度、遇到的问题、最后执行时间
> - 若上述文件缺失或为空，标注将基于 spec.txt 从头规划
>
> **步骤三：生成日程规划建议**
> 基于上述文件信息，生成日程规划建议。核心原则：规划的任务必须在 Agent 能力边界内可执行，超出能力范围的任务单独列出并说明原因。
> 1. 现状评估：总结当前进度，明确已完成和未完成的部分
> 2. 差距分析：对比目标与现状，识别剩余工作量
> 3. 能力评估：区分可执行任务和受限任务（需特定外部工具、线下操作、专业人工介入等）
> 4. 日程编排：将可执行任务拆解为阶段性任务，分配时间节点，按依赖关系和紧急程度排定优先级
> 5. 输出结构化的日程规划，包含：每阶段目标与交付物、时间安排、关键检查点、**每项日程的具体描述（发给日程子 Agent 执行的 Query）**、受限任务清单及替代方案建议、需用户配合的事项

多个计划的后台任务同时分派，并行执行。

#### 2.2 接收结果并推进

每个后台任务返回后，立即在主对话中对该计划执行（无需等待所有后台任务完成）：

1. **重新阅读 spec.txt**：读取 `{目标路径}/history/spec.txt`，在主对话中建立该计划的完整上下文，确保计划信息不丢失
2. **呈现规划**：结合 spec.txt 内容与后台任务返回的规划建议，向用户展示现状评估、规划概要、受限任务及替代方案建议（如有）
3. **征求确认**：与用户讨论调整，等待确认
4. **创建日程**：用户确认后，调用 `calendar_create` 工具创建该计划的日程。**强制要求**：日程描述中提及的所有文件路径必须是迁移后的目标路径下的路径（即 `{目标路径}/...`），确保日程执行时路径引用正确

## 注意事项

- 始终尊重用户选择，不跳过沟通环节直接执行
- 文件复制失败时做好错误隔离，单个计划失败不影响其余计划
- 规划日程时充分参考历史执行记录，避免重复已完成的工作
- 规划结果应具体、可执行，避免空泛的描述

## 常见 Q&A

当用户询问以下问题时，参考对应回答：

1. **为什么要迁移/重启长期计划？**
   - 因为在扣子新版本中，长期计划全面升级为日程，且升级后不再限制长期计划创建数量。之前旧版本的长期计划需要迁移到新版本中才可以继续自动执行推进。

2. **应该怎么迁移/重启长期计划？**
   - 直接在新版对话中要求重启之前的长期计划，我会自动帮你完成之前长期计划中的文件迁移，并且规划新的日程继续推进。

3. **之前的长期计划数据会丢失吗？**
   - 不会的，之前的长期计划中的对话和文件数据，都可以在历史话题-对应长期计划中查看。

4. **只有一次迁移重启机会吗？**
   - 不是的，可以在后续想要迁移的时候随时在对话中要求「迁移长期计划」。
